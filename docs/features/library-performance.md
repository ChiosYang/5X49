# 片库扫描与保存性能

状态：Done

## 验收口径

- 在种子 549 的同一份千部影片目录上，用三个空数据库分别完成首次扫描和原目录复扫。核对影片及版本标识、任务状态和轮询结果。另在部分影片已提交时取消扫描，经正常工作流重试后核对重复与缺失。
- 与[原始基准](performance-baseline.md)使用相同的读写工作负载。千部片库收藏、修改原始片名和新建观影记录的 P95 目标均为 200 毫秒以内。写后立即读取详情、日记与 Cinema DNA。
- 对同一数据库快照分别运行新旧合集查询，逐项比对输出，包括分页、推荐、分类、数量、未观看数和封面。分别多次测量固定 TMDB 响应下的确认匹配和单文件整理。

## 实现

扫描按批提交，批内检查取消状态和媒体目录时复用写入连接。各批独立记录新增数量，所有根目录完整扫描之后才处理缺失。写前校验和实际入库在同一事务内，发生错误时回滚当前批次。

详情和片库卡片共用一次影片数据读取。SQLite 按主键和来源哈希生成与原版一致的有序 JSON，应用计算 SHA-256。写入、派生数据和校验摘要仍在同一事务内提交。合集目录只读取成员分组、预览排序和未观看计数所需的字段，数据库先筛出有导演角色的成员。

扫描及单部匹配、整理所用的视频信息缓存通过一次查询读取主版本和首个有效视频，省去了逐部构造完整影片详情的工作。新增回归用例覆盖切换主版本、忽略全部版本后缓存的内容。

## 验证记录

使用同一条真实扫描路径，将 SQLite 缓存缩至 4 页。在基准版本上，写事务期间从另一连接读取任务取消状态时出现 `database is locked`。修复后的扫描测试与中断重试回归测试均通过。

### 千部目录扫描

三轮使用同一份实体测试目录，1,000 个视频和 1,000 份 NFO 的路径与内容摘要固定。每轮从独立空库经正常 API 扫描，再复扫同一目录。在每轮前后核对全部影片 ID、TMDB 标识及主版本 ID。轮询每次分别读取工作流和扫描状态。

| 轮次 | 首次导入 | 原目录复扫 | 复扫新增 / 缺失 | 成对状态读取次数 |
|---|---:|---:|---:|---:|
| 1 | 444.08 秒 | 120.02 秒 | 0 / 0 | 1,437 |
| 2 | 215.74 秒 | 140.05 秒 | 0 / 0 | 965 |
| 3 | 197.86 秒 | 118.58 秒 | 0 / 0 | 941 |

三轮均得到 1,000 部唯一影片、1,000 个唯一主版本，每次复扫前后身份一致。六次扫描共完成 3,343 对状态读取，HTTP 错误为零。首次导入耗时受机器并行负载影响明显。独立的原版全栈基准另一次首次导入和复扫分别耗时 176.12 秒和 134.46 秒。

第四个空库在导入途中通过正常工作流取消，任务停止时已提交 300 部。对同一任务调用重试，124.32 秒后成功补齐其余 700 部。取消后和重试后缺失数均为零。四个数据库的最终 TMDB 标识集合逐一匹配全部 1,000 份 NFO，每个数据库均只有 1,000 个可用版本。

### 原版全栈基准

正式参考数据测于产品版本 `f9dfbd4`，本次修复测于 `3daacbe`，包含已合入主分支的详情页更新。以下为 `npm run test:perf` 在 1,000 部片库上的 HTTP 延迟，单位为毫秒。每个写入采样 20 次，合集读取采样 25 次。

| 操作 | 原基准中位数 / P95 | 修复后中位数 / P95 |
|---|---:|---:|
| 切换收藏 | 331.49 / 350.49 | 100.00 / 105.90 |
| 修改原始片名 | 331.80 / 360.34 | 100.73 / 111.48 |
| 新建观影记录 | 332.36 / 339.11 | 100.01 / 108.41 |
| 合集目录 | 91.24 / 177.25 | 66.76 / 96.70 |

本机同时运行了独立的扫描稳定性验证。12 部片库在这次全栈测量中出现尾部波动，三项写入 P95 依次为 157.62、134.98 和 230.14 毫秒，原基准为 117.10、124.78 和 122.61 毫秒。另用同一份 12 部快照同时启动两个版本，以正反顺序交替发送同样的写入，每项各采样 20 次。收藏 P95 为 73.16 → 75.08 毫秒，元数据为 82.09 → 76.35 毫秒，观影记录为 90.79 → 80.33 毫秒。小片库的尾延迟仍需结合运行时负载解读。

### 同一数据库快照对照

用同一份包含 1,000 部影片和 200 条观影记录的 SQLite 快照分别启动旧版和新版。每次通过真实 HTTP 请求读取或保存，同一对照使用同一客户端和预热次数。保存后立即核对详情、日记或 Cinema DNA。以下为专项对照，单位为毫秒。

| 操作 | 每版样本数 | 旧版 P95 | 新版 P95 |
|---|---:|---:|---:|
| 切换收藏 | 20 | 383.11 | 136.62 |
| 修改原始片名 | 20 | 462.52 | 133.15 |
| 新建观影记录 | 20 | 394.90 | 127.39 |
| 合集目录 | 25 | 174.37 | 82.68 |

8 组目录查询的完整响应经规范化 JSON 编码后逐字节一致，包含推荐、翻页、分类和搜索。使用旧版完整校验器读取新版保存后的 8 张派生表，共 13,236 行；再用旧版重新生成被编辑影片的派生数据，8 张表的行数和完整摘要均一致。

另在生产版 Chromium 页面上实点收藏和编辑片名，重新打开详情后核对两项结果。通过日记表单新增带 4 星评分和备注的观看记录，立即重新打开日记核对片名与备注，Cinema DNA 页面显示的记录数从 200 变为 201。

### 单部匹配与整理

每次从独立的同一数据库快照开始，使用固定 TMDB 响应。三次独立测量的中位数如下。整理计时从提交确认开始，到工作流成功结束为止。逐次核对视频内容、同名 NFO 和原路径移除。

| 操作 | 旧版中位数 | 新版中位数 |
|---|---:|---:|
| 确认元数据匹配 | 34.36 秒 | 0.73 秒 |
| 确认整理单个视频 | 68.12 秒 | 1.87 秒 |

## 复核

在 `frontend/` 运行 `npm run test:perf` 可生成同格式的完整报告。在相同机器与数据规模下使用比较脚本复核不同版本。正式对照保留了全部 4,362 个样本，专项记录另存了每次扫描、取消重试、目录快照对照、浏览器即时读取及兼容性验证的数据。[正式修复后样本](../evaluations/performance-library-fix-v1.json) · [专项验收数据](../evaluations/library-performance-acceptance.json)

```sh
node e2e/performance/compare.mjs ../docs/evaluations/performance-baseline-v1.json ../docs/evaluations/performance-library-fix-v1.json
```

这些数据测自 Windows 本机、合成媒体和真实 SQLite。TMDB 使用固定响应。在线 TMDB 往返和真实 NAS 的磁盘表现需要在对应环境测量。三次维护操作报告中位数，扫描失败历史只计失败耗时。
